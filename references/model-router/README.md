# Model router operator reference

The shared model router picks a model for a work category and a Codex or Claude lane. It keeps the established choices while evidence is being collected, then uses a researched table to rank eligible models. Protected work and long-form writing have stricter routing rules. `scripts/model-router/resolve-model.ps1` is the entry point; callers can request `-Json`.

Code lives in `scripts/model-router/`. Committed configuration and the starter table live in `references/model-router/`. Runtime files, including the live `router-table.json`, model registry, check stamp, research profiles, alerts, outcomes, and cost reports, are per machine. `Get-RouterStateDir` in `scripts/model-router/router-common.ps1` resolves that folder: `DT_MODEL_ROUTER_STATE` when set, otherwise the `model-router/state` sibling of the main checkout. The same state folder is used from a worktree, and its `.gitignore` containing `*` keeps its contents out of Git.

The router stays in **bridge mode** until a full research table is approved. Its first picks follow the pre-router tiers, and a retry escalates at most to the top non-frontier model (GPT-6 Sol, Opus); frontier models run only on Danny's explicit request through `-Model`. A valid research table needs `coverage=full` and `evidence_routing_approved=true` before evidence changes a pick. An invalid live table falls back to the seed and raises an alert.

The lookup makes no network call. The model catalog check runs offline twice a day from `run-router-cadence.ps1` (01:00 ET full run, 13:00 ET check only) with a 30-second deadline. New models are recorded and queued for research; a newly detected model also triggers a detached canary. A timed-out or failed check preserves the last good registry. Alerts show a chat line, then try a private Discord DM, with email as fallback. A delivered alert key fires once; its delivery is recorded in `alert-log.jsonl`.

`run-router-research.ps1` writes each accepted profile to `profiles/<model>.json` and an unoverwritten timestamped copy in `profiles/history/`. `build-router-table.ps1` reads the latest profiles and their history. A category grade is confirmed only when the two newest history runs agree and each cites an independent source; the latest raw grade remains visible. The bridge pick is the incumbent. Research can replace it only with a confirmed non-frontier model that grades higher, or grades equally and has lower calibrated expected cost. An older generation from the same vendor needs a higher grade; an unknown incumbent stays put. For example, confirmed strong GPT-5.6 Sol may replace capable GPT-6 Sol, but an equal-grade older Sol cannot win on cost alone. An unknown Opus keeps the Claude writing pick instead of moving it to frontier Fable. Protected work and writing move only to a larger model in a fixed size order (Haiku < Sonnet < Opus < Fable; Luna < Terra < Sol < Astra), never to a frontier one, so in practice they stay on Opus and GPT-6 Sol. When outcome drift flags a pick, the router moves to the next qualifying unflagged model, then the incumbent, then one ladder rung up; it never steps onto a frontier model or one confirmed weak for that category, and alerts when no move is possible.

After research, run `pwsh -NoProfile -File scripts/model-router/approve-router-table.ps1 -Show` to review every ordinary and protected pick, then `-Approve` to enable the new table or `-Revoke` to return to bridge mode. A rebuild that changes an approved pick clears approval and alerts for another review. `update-outcomes.ps1` reads build outcomes, tunes measured pass rates, and flags performance drift; the resolver can demote a flagged model when an eligible alternative exists. The weekly cost report compares subscription use with estimated API-equivalent spend, and also DMs a short plain-language summary of the last complete week (subscription vs API-equivalent cost, most-used models, frontier use, Codex quota, and anything pending Danny's OK) through the same Discord alert channel. The monthly canary tests selected and flagged models and records outcomes; it also runs after a newly detected model release.

## v2: one roster across both vendors

v2 routes delegated work from a short roster (at most 5 models) defined in `roster-schema.md`. Eleven categories map to five jobs: `mechanical` to fast; `routine-coding`, `complex-coding`, and `ui-frontend` to coder; `code-review`, `planning`, `deep-research`, `math`, and `analysis` to deep thinker; `long-form-writing` to writer; `image-generation` to illustrator. Each job has a first choice and a backup on the other vendor; the illustrator has no backup while only one image model exists. Frontier models are never on the roster.

The resolver uses the roster only once `<state>/roster.json` is approved; until then the v1 table and bridge mode above keep routing, and calls without `-Lane` take their lane from `default-roster.json`. A caller that passes `-Lane` gets that lane's member of the pair or a `wait`. A caller without a lane gets the first choice, or the backup when the first choice's vendor is at its limit (`vendor-limits.ps1`: Codex at 95% weekly use from local session logs, or a recorded refusal), unselectable, or drifting. Both vendors blocked returns `status = wait`, never a weaker model.

Research runs per category (`run-router-research.ps1 -Categories`), reading the named sources in `benchmark-sources.json` and storing readings under `<state>/readings/`. `build-roster.ps1` turns readings into a proposal: two independent comparable leads and no trail win a category; the job's primary category decides a multi-category job; a change needs two consecutive conclusive passes that covered the job; the fast job clears a quality floor, then the lower list price wins. A change sends one Discord DM and writes a report under `<state>/roster-proposals/`.

Manage the roster with `approve-router-table.ps1 -Roster`: `-Seed` (first proposal from today's picks), `-Show`, `-Approve` (switches routing to the roster), `-Revoke` (back to v1), and `-DeclineDrift -Job <job>` (keep the first choice after a drift alert). Drift on a first choice sends that job to its approved backup until Danny approves the swap proposal or declines it.
Use `-Approve -Jobs fast,coder` to approve only named jobs when a full proposal exceeds the five-model cap.

At ship, register the Windows Scheduled Tasks from the **main checkout** with `pwsh -NoProfile -File scripts/model-router/register-router-schedules.ps1 -Apply`. They run the monthly canary on day 1 at 04:00 ET, the weekly cost report on Monday at 07:00 ET, the full research cadence daily at 01:00 ET, and the model-release check daily at 13:00 ET. Do not register them from a build worktree.
