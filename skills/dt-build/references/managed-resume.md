# Managed coordinator resume

Resume an existing authorized run; do not repeat intake. The launcher supplies run id, folder, checkpoint, host and coordinator id. `<skill>` is this skill's resolved folder; `<danny-skills>` is the repo root two levels above it. Quote substituted script paths.

## Before marking bootstrap

1. Follow the system instructions first. A lean Claude coordinator receives the live canonical instruction chain in its generated system prompt; do not reread those CLAUDE.md files. A bridge declaring `mode="dt-build-lean"` defers the canonical chain until its action needs it. Otherwise complete required bridge reads fresh, fully and in order. Required authorization reads are never optional.
2. Run the single entry command alone: `pwsh -NoProfile -File "<skill>/scripts/read-coordinator-rulebook.ps1" -CoordinatorHost <host>`. Apply its complete authority contract and shared policies once. Do not preload execution rules, full roadmap/design, canonical git/model-routing/build-process policy, script source, intake, history or close-out references. Policy triggers fire when actually taking the governed action, not while reading state.
3. Run `pwsh -NoProfile -File "<skill>/scripts/read-coordinator-state.ps1" -RunFolder <folder> -RunId <id> -BuildStatePath <checkpoint> -CoordinatorId <coordinator>`. Read the complete output. It verifies identity/lease/runnable status, emits the full checkpoint and run records (including complete approvals and operator notes), current roadmap rows as navigation, verified authority index and every mandatory original. Operator notes override checkpoint claims. Navigation grants no authority. The script fails closed on missing, changed or oversized authority; follow the authority contract's fallback, never omit reads to meet a budget. If it returns a multipart read plan, read every numbered part using `-Part <number> -ExpectSha <sha256 from plan>` before marking. A hash mismatch fails the read: restart from the plan and read every part again. Never replay an already seen persisted tool output in full.
4. Immediately run `pwsh -NoProfile -File "<skill>/scripts/dt-job.ps1" -Verb mark-bootstrap -RunFolder <folder> -CoordinatorId <coordinator> -Host <host> -Json`. No job evidence, reconciliation, dispatch preparation or implementation reads precede this marker. Target at most 20,000 coordinator-added input tokens; retain the actual context baseline. Marking is measurement, never permission. Stop on contradictory authority.

## At approval stops

Stops can occur at any time. Raise one through `<skill>/scripts/dt-job.ps1 await-danny -WaitMinutes 7.5 -CallStartedUtc <UTC captured before pwsh launch> -Json` with tool timeout `600000`. A live director can approve while the call blocks and renews the lease: on `decision=approved`, read the receipt and continue in the same coordinator; otherwise checkpoint and end. Never re-wait the boundary or self-approve. The launching session owns `resume`, `approve`, `delegate` and `hold`; never ask Danny to type them.

## Carry on

Quiet I/O-bound work receives a director stop at 40 minutes without sustained progress; it is never killed. Repeated lines modulo timestamps/counters and brief CPU/file bursts preserve the first stall and acknowledgement count: periodic chatter cannot evade the two-hour limit. Recovery requires progress across 80% of five minutes. Cap acknowledgements at the default stop plus 70 minutes and at 110 minutes since progress. Each renewal forces one stop; approval covers it until expiry. An explicit keep after the cap grants at most two hours from approval. Existing stops retain deduplicated facts and delivery.

**Stalls require action in this turn.** On `result=stalled` or a stalled job in status/reconcile, inspect the command, recent output and process tree and identify the dependency it waits on. Cancel/fix it, or record `dt-job stall-ack -CoordinatorId <id> -JobId <job> -Reason "<dependency and why keep waiting>" -Until <minutes>`. Never consume the stall and repeat a wait without a decision. Acknowledgement preserves the stall and adds a deadline; expiry interrupts waits again. The watcher independently routes a stop to the director at 2x the stall period (40 minutes idle by default), or at the acknowledged deadline. The director decides cancel/fix or keep with a new acknowledgement, and approves the `stalled-jobs` stop to continue. Acknowledging alone does not approve an existing stop. No job is killed on time. A live director receives every stop; Danny is DMed once per boundary only if no live director exists. Sustained progress clears the stall episode; an already-raised approval stop still needs its decision.

- After marking, load the entry's applicable named sections before the next action: `execution`, `context`, `guardrails`, `adapter`; add other sections only at their listed triggers. This is not intake. Reconcile existing jobs before consuming events, inspecting report verdict and failure category as well as process status.
- Use supplied paths, never a recursive workspace search. Never run `resume`, `approve`, `delegate` or `hold`, replace registration or reacquire the watcher lease. The launching session owns operator commands; never ask Danny to type them. An existing approval never authorizes a new merge, push, deploy, production write or irreversible operation.
- On a context wall, send heavy evidence to a mechanical worker after bootstrap; required instruction/policy/authority reads remain mandatory. Read an automatic kill handoff after marking and confirm its jobs against the ledger. Reuse recorded worktrees on the right base; verify branch/scope before adding one.
- Reference packs are frozen contract data, not current policy or approvals. Verify their hashes and load only applicable contract sections before gates. Workers perform their own governing reads. Dispatch through dt-job and the host adapter without `-Model`; the run pin is enforced by wrappers. Long tests and audits are jobs. Use capped envelopes and read-evidence for deeper evidence.
- Before rotation load the `context` and `checkpoint` sections. Consume handled events, preserve dt-job-owned checkpoint fields, request context_rotation, release the lease and end. Running jobs survive; rotation without new job progress remains thrash.

## Lean checkpoint

Job lifecycle events refresh `status_line` automatically with current running jobs, waiting count, and the latest event. The checkpoint writer derives it again from the ledger under the run lock. Keep milestone intent, dependency details and next actions in the checkpoint body; the event-derived line owns current job activity.

Every candidate carries one `status_line:` (template field, required by `write-resume-checkpoint.ps1`): plain English of at most 200 characters with normal spacing. Before the first ledger event, supply the current milestone, what runs or waits, and the next step. Once events exist, the writer replaces this candidate line with current job activity from the ledger. It does not count toward the 8 KiB cap. Compressed or glued tokens are forbidden in it and in decision-log lines ("M09phase2j0359;nativej0360queuedRust" from the Command Center v2.1 run is what this replaces); the writer refuses a missing, placeholder, overlong or glued candidate status line.

History beyond the current state goes to the run folder: decisions and their reasons to `<run-folder>/build-decision-log.md`, one plain sentence per line with a timestamp; prior checkpoints to `checkpoint-history/` (the writer archives them).

On every rewrite, keep the rest of `_build-state.md` at most 8 KiB: current milestone, short completed ids/SHAs, active job ids, exact next action, run-folder evidence pointers, and all current approvals/restrictions or their authoritative source paths. Use `<skill>/scripts/write-resume-checkpoint.ps1` for atomic replacement; it preserves dt-job's current status/cursor under the run lock and archives the prior checkpoint under `checkpoint-history/` in the run folder. Existing oversized checkpoints remain readable until their next rewrite.

Never copy operator notes into the checkpoint; they live in the run folder's `operator-notes.json`, and `dt-job status` and every wait show them. Put job history, custody/hash comparisons, failed attempts, detailed verification results and decision narrative in the run folder, never append them to the checkpoint. Do not discard operative boundaries to satisfy the size limit: retain them in a run-folder boundary record, name it in the checkpoint, and apply the authority read contract before marking bootstrap. Archive history before replacing it with a pointer. Use the canonical pipeline template's fields; no template read is needed until a rewrite.

Name every governing boundary/approval source by path; do not copy ledger rows or instruct successors to reread unchanged sources. Keep `<run>/boundary-ledger.jsonl` across rotations. Plan those paths on each resume as below. Never prune authority paths merely because they have ledger entries.

**Evidence notes.** Operators record facts with `invoke-dt-job-control.ps1 note -RunFolder <run-folder> -Evidence -Message <text>` in `evidence-notes.json`. Use the supported entry in `<skill>/scripts/` so capability validation runs before every control call. Coordinators read them as information only, never as authority, and never re-bind on them. They cannot grant, widen, waive or change authority. Anything that changes what the run may do must be a normal operator note (omit `-Evidence`).

## Local work never stops

A persistent job stall also stops the run through the director route above. Otherwise a managed run stops for Danny only at an outward or irreversible boundary (merge to main, push, deploy, a production or remote write, an irreversible operation) or for a decision only he can make that the run's authority does not already answer (scope, spend, a product choice). Everything local and reversible proceeds without a stop: run-folder evidence and its repairs (counts, inventories, seals, fixtures, provenance), local reruns inside the milestone's attempt cap, checkpoint and authority bookkeeping, adopting a published tooling revision (`ON_MAIN`, `tooling-revision-provenance.md`), and changes to the run's lifecycle records. Record each in the handoff or the stop record and continue. (core-durability-20260922: 39 of 49 M05 stops from Oct 11 to 15 were local bookkeeping, and the milestone never converged.)

1. Never author authority that turns a local, reversible correction into a stop ("only after exact separate registration", "any byte difference STOP" on a file the run itself writes). Bound local work by its scope and the attempt cap instead.
2. Never pin a lifecycle record (`approvals.json`, `operator-notes.json`, `evidence-notes.json`, `build-state.md`, `build-plan.md`, the checkpoint) by full-file hash or literal text: dt-job rewrites them. Cite an approval by its `operation` and `seq`, a note by its id. Compare timestamps as instants, never as text.
3. Evidence for a local acceptance milestone is content evidence: each input's SHA-256 when it was captured, plus the test and validator results. Byte-prefix and literal-text custody is only for files whose exact bytes something consumes (a pinned wrapper a remote host runs, a host key).
4. When a run's existing authority already requires a stop for local work, follow it, but say `local stop` in the `await-danny` message and recommend the operator note that lifts it. Never add another such clause.

## Launch watch (the session that launched the run)

A launch is not done when the command returns. On 2026-11-22 (Home Server run mst-20261122) the launching session declared success after one 20-second check; both coordinators exited 1, the watcher stopped the run for thrash, and nobody looked for 2 hours. After a managed start, a resume, a relaunch it asked for, or an approval that re-arms the run, the launching session:

1. **Confirms the start.** Run `pwsh -NoProfile -File "<skill>/scripts/await-coordinator-start.ps1" -RunFolder <run-folder> -TimeoutSec 600 -Json` (Bash `run_in_background: true` on Claude Code; foreground on Codex). It reads `launches.jsonl`, the bootstrap mark in `context-baseline.json`, and `coordinator-<id>.exit.json`, and returns `started` (exit 0), `exited` with the exit code and the log tail (exit 1), `stopped` when the watcher stopped the run or it left runnable (exit 1), or `timeout` with the pending coordinator's log tail (exit 2). It ignores launches before the newest continuation request; `-SinceUtc` overrides that.
2. **Reports a failure, never a success it has not seen.** On `exited`, read the log tail (`read-evidence.ps1 -Path <log>` for more), state the cause in one plain sentence, and fix what is the session's to fix (a wrong path, a missing tool, a failed preflight per "Lane health") before relaunching. On `timeout`, read the log once more and say the coordinator has not started yet; never call it started.
3. **Arms the background status watch.** Run `pwsh -NoProfile -File "<skill>/scripts/watch-run-state.ps1" -RunFolder <run-folder> -Json` with Bash `run_in_background: true` (build-process.md, "Watch a dt-build run with a background wait"). It stays silent and exits only on a change: `run_status` (a stop, approval wait or finish), a new awaiting boundary, a job ending failed, timed out, orphaned or blocked (worker death), a newly stalled job, a coordinator that died holding the run or overran its starting window, or a runnable run with no coordinator for 10 minutes. A normal rotation is not a change. `quiet` (exit 2, after 55 minutes) means re-arm it. On a wake, act (relaunch, approve, fix) and tell Danny only what needs his decision; never post routine progress.

The coordinator lease is `starting` from the launcher's acquire until the coordinator marks bootstrap, at most 15 minutes. `dt-job status -Json` reports it as `coordinator.state` (`none`, `starting`, `running`, `released`, `gone`, `boot_overdue`, `expired`). A starting coordinator is not missing; past the window with its process alive, the watcher sends Danny one `boot-overdue` DM and still never starts a second coordinator beside it.

## Worker authority scope

The authority read contract binds the coordinator, not its workers. Workers never re-read the run's whole authority set; when the set exceeds the 32,000-character soft target, a brief that tells a worker to read every governing original only spends the worker's context before it does the work (core-durability-20260922, Oct 14: two source-preparation workers checkpointed at 18 and 64 of 130 originals without preparing source).

1. Before dispatch, the coordinator completes its own full reads, then writes the worker's restrictions into the brief as operative rules: allowed paths and operations, exclusions, pins, required evidence, and stop conditions.
2. The brief names only the originals whose exact text the worker's task consumes (a spec, a pinned input, a locator), within the 32,000-character soft target. The worker reads those in full, with `read-authority-original.ps1` when the brief asks for verified reads.
3. If the task needs more authority than fits, the worker stops with a continuation note naming what it needs; the coordinator resolves it. A worker never reconstructs authority from summaries.
4. The coordinator verifies worker output against the full authority, with fresh full reads per item 4 of the read contract, before any dependent merge, push, deploy, production write, approval-gated step or irreversible operation. A worker's reads never stand in for the coordinator's.

This scope changes no approval or restriction: the coordinator still holds every governing original, and workers still act only inside the restrictions written into their brief. The authority roll-forward below keeps the coordinator's own set small; it is not a remedy for worker context.

## Authority roll-forward

Each stop inherits every earlier stop record, so a long run's action-time read set only grows (core-durability-20260922 reached 146 originals and 654,965 characters on Oct 15, past what one coordinator can read). The roll-forward cleans up after itself: at a stop or approval transition, once the action-time read set passes the 32,000-character soft target, roll the governing stop records into ONE current record that carries every live clause verbatim and drops the stale ones with evidence. Old stop records stay on disk untouched as evidence; they leave the read set. Lifecycle records (`approvals.json`, `operator-notes.json`, `build-state.md`, `build-plan.md`, the checkpoint) are never rolled.

1. `<skill>/scripts/roll-authority-forward.ps1 -Action prepare -RunFolder <folder> -BuildStatePath <checkpoint>` splits every stop-record original in the current graph into clauses (Markdown paragraphs and list items, JSON fields), merges identical text into one row that keeps every origin, and writes `RUN/authority-rollover/<utc>/clauses-ledger.json`. Graph-wiring JSON fields are pre-marked `structural`.
2. Decide every undecided clause in the ledger: `carry`, or `drop` with `reason` (`consumed`, `superseded`, `closed`, `exhausted`) and checkable `evidence`: `{quote: {path, text}}` found in that file, `{event_seq: N}` in `jobs/events.jsonl`, or `{clause: "c-..."}` naming the carried clause that supersedes it (a superseding clause later folded into a consolidated clause still counts, through that consolidation). Carry when in doubt; a carried stale clause costs a few characters, a dropped live one removes a restriction. When one rule is restated across several stops in different words or numbers, replace the restatements with one consolidated clause: add `{text, heading, replaces: [c-ids], why}` to `<dir>/consolidations.json` (at least two replaced clauses, each replaced once) and mark each replaced clause `drop`, reason `consolidated`, evidence `{consolidation: "<id of that text>"}` (ids are `c-` plus the first 12 hex of the SHA-256 of the whitespace-normalized text). A consolidated clause must keep every restriction, pin, gate, allowance limit, exclusion, scope, exception and number of each clause it replaces, with the strictest value winning. Never edit a clause's id, text, heading or sources. For a large first roll, the coordinator may brief a worker to draft the decisions; verify and the review below still guard every drop.
3. `-Action compose -RolloverDirectory <dir>` writes `current-authority.md` (carried clause text only, verbatim, grouped under each original heading once, with consolidated clauses under "Consolidated restatements"), `current-authority.provenance.json` (each clause's id, record lines and RUN-relative sources; evidence only), the rollover `next-operation-boundary.json`, and `review-prompt.md`. Its result reports `record_chars` against the digest's read ceiling (`within_ceiling`); over the ceiling, drop or consolidate more before review.
4. Dispatch exactly one independent reviewer: `invoke-codex-chunk.ps1` or `invoke-claude-chunk.ps1` with `-ReadOnly -AdHoc -SingleDispatch -PromptPath <dir>/review-prompt.md -OutputPath <dir>/review.json`. It answers `stale` or `live` for every dropped clause, and `covers` or `loosens` for every consolidated clause. The review must be independent: compose moves any earlier review in the rollover folder (and the current `review.json` whenever the prompt changes) to `RUN/authority-rollover/_review-archive/<rollover>/<utc>/`, the prompt forbids consulting earlier reviews, and verify refuses while an earlier review sits in the folder. The reply must be the JSON object alone; a prose preamble fails verify.
5. `-Action verify -RolloverDirectory <dir>` proves nothing live was lost: the same STOP boundary and originals as prepare, unchanged hashes, a ledger equal to a fresh extraction, every clause decided, drop reasons from the closed set with evidence that exists, every consolidation well formed and matched by its consolidated drops, a record and sidecar equal to compose output, a record within the read ceiling, and a passing single-dispatch review whose prompt and output hashes match, which names the same consolidations file and calls every drop `stale` and every consolidation `covers`. Any failure stops the roll; fix the ledger, compose again, and review again.
6. `-Action install -RolloverDirectory <dir>` re-verifies, appends every dropped clause to `RUN/authority-history.jsonl` (verbatim text, source path, locator and sha256, reason, what superseded it, the reviewer's reason, the time), points the checkpoint's `STOP=` at the rollover through `write-resume-checkpoint.ps1`, then rebuilds and verifies the authority digest. Its report gives the new read set and any pre-rollover original the checkpoint still names (`still_required_old_records`); remove those pointers in the next checkpoint write. A checkpoint line that names stop-folder files (`STOP/next-scope.md`, `STOP/source-disposition.json`, `STOP/next-approval.md`) would resolve into the rollover, which holds only the record and its boundary; install refuses with `AUTHORITY_ROLLOVER_CHECKPOINT_POINTERS` naming those lines. Rewrite them first through `write-resume-checkpoint.ps1` to `STOP/next-operation-boundary.json` and the originals it enumerates, which is equivalent under the current STOP. `-CandidateOnly` previews without writing; its `consolidated_clauses` lists every consolidated clause with the ids it replaces. Consolidated clauses are new wording: the independent review's `covers` verdict and verify guard them, and the coordinator records the preview path in its handoff so Danny can read it; the install is bookkeeping and never waits for his go. History rows for consolidated originals also carry `consolidated_into`.

The next stop's boundary sets `inherited_boundary` to the rollover's `next-operation-boundary.json`, so its read set is the current record plus the new stop's own records, and the next roll starts from there. Clause ids are content hashes, so a carried clause keeps its id and original source across rolls. `authority-history.jsonl` is append-only audit history: digest discovery treats it, the provenance sidecar, `consolidations.json` and the ledger as evidence only, and it is never read before an action. Read it only to look something up. The roll-forward changes no approval, restriction, pin or gate: every live clause stays in the read set word for word, and the read contract above applies to the current record like any other original.

## Operator recovery after an authority wall and thrash stop

For read-only acceptance, add `-DryRun -OutputDirectory <external-folder>` to the builder and `-DigestDirectory <external-folder>` to the verifier. DryRun requires output outside both the run and checkpoint directories, and never publishes a live digest or pin. Inspect originals discovered, unresolved candidates, Markdown/bootstrap characters, deferred original bytes and mandatory full-read bytes in the verification result. A failed build writes discovery diagnostics at its output location and grants no authority.

After the release coordinator installs this fix, an operator can build and verify the digest before re-arming the stopped run. These commands write the digest only when the operator runs them; do not execute them during fixture-only development. Obtain the registered checkpoint from the dt-job registry for this run (no recursive search): (the example is the 2026-09-22 File Sorter run, which lives on SNOWWHITE; on the Linux host use `/home/danny/Claude/...` paths and run the block inside `pwsh`)

```powershell
cd "D:/Claude/_Claude-Workspace/Skill Creation/danny-skills"
$recoveryRunFolder = 'D:/Claude/_Claude-Workspace/OneDrive Migration/File Sorter/file-sorter/.dt-build/core-durability-20260922/core-durability-20260922'
. ./skills/dt-build/scripts/dt-job.ps1
$registration = Get-DtJobRegistryEntry -RunFolder $recoveryRunFolder
if ($null -eq $registration) { throw 'Run registration missing; keep run stopped' }
pwsh -NoProfile -File "<skill>/scripts/build-authority-digest.ps1" -RunFolder $recoveryRunFolder -BuildStatePath $registration.build_state_path
if ($LASTEXITCODE -ne 0) { throw 'Digest build failed; keep run stopped' }
pwsh -NoProfile -File "<skill>/scripts/verify-authority-digest.ps1" -RunFolder $recoveryRunFolder -BuildStatePath $registration.build_state_path
if ($LASTEXITCODE -ne 0) { throw 'Digest verification failed; keep run stopped' }
```

Then issue `/dt-build resume core-durability-20260922` in the operator session. This clears the thrash stop and re-arms the launch budget; the coordinator never issues resume itself. It reads current authority and the verified digest before marking and the governing originals before actions. Capacity refusals use separate 5/10/20 minute backoffs with a 35-minute total wait bound; exhaustion pauses with reason `capacity` and a distinct alert, without spending thrash, retry or launch-cap budgets. A later resume re-arms that budget too.
