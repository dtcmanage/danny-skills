# Managed coordinator resume

This is the entry contract for a watcher-launched coordinator, on either host. It resumes an existing authorized run; it does not repeat intake. The launcher supplies the run id, run folder, checkpoint path, host and coordinator id. Resolve script paths from this reference's skill folder, resolving a skill junction before walking to the repo root.

## Before marking bootstrap

1. When the bridge declares `mode="dt-build-lean"`, defer the canonical chain and root policy until the action needs them. The launcher sets `DT_BUILD_LEAN_BOOTSTRAP=1` only for headless Codex coordinators; it grants no authority. Otherwise complete the bridge's required reads fresh, fully and in order, without rereading native files; never reread a complete read, as the hook denies the third full read of a file and points to read-evidence slices. Read each file separately with enough output capacity; never batch full files into truncated or nested JSON output. Required authorization reads are never optional.
2. Read this reference and run `pwsh -NoProfile -File scripts/read-coordinator-rulebook.ps1 -CoordinatorHost <host>` from this skill's resolved directory. This emits exactly one host adapter plus current SKILL.md Model routing, Context discipline, milestone execution and Guardrails sections. It fails closed if a section is missing. Read the repo's `references/deterministic-reference-policy.md` and `references/conventions.md`. In ordinary mode read canonical `build-process.md` once; in lean mode defer it until a new build or close-out. Do not load the full skill, intake schemas, script source, template, session-audit skill, tech stack, brandbook or history during bootstrap. Gate contracts still load before their gates.
3. Read `_build-state.md` in full and the run's `build-state.md` and `build-plan.md`. Run `pwsh -NoProfile -File scripts/read-resume-record.ps1 -RunFolder <folder> -RunId <id> -BuildStatePath <checkpoint> -CoordinatorId <coordinator>`: it reads and verifies the registered run record, complete approvals, operator notes, lease and current status/cursor. A run pin is enforced by dt-job and wrappers: dispatch without `-Model` and never restate it in handoffs. Operator notes are standing instructions from Danny or his operator session: follow every one, ahead of anything in the checkpoint. A `context_wall` means earlier coordinators used up their working room without starting a job, including before bootstrap. Route inherited authority through the verified authority digest below; send other heavy evidence reads to a `mechanical` worker. The wall never blocks instruction and policy files (CLAUDE/AGENTS/MEMORY/CONTEXT.md, `00_Resources` policy, skill `SKILL.md` and references): read a triggered policy whole yourself. A `kill_handoff` is the watcher's note for a coordinator stopped before it could hand off; read it, then confirm its jobs against the ledger. `worktrees` lists the trees this run's coordinators created (recorded and live); before adding a worktree, reuse the one on the right base rather than creating a parallel one. Verify branch and scope. Follow the authority read contract below: original records and explicit restrictions control authorization, even when a digest or summary says PASS. Missing or contradictory authority stops the dependent action. Never infer new authority from a previous coordinator's claim or a reference pack.
4. Use the supplied run folder, not a recursive workspace search. Never run `resume` or `approve`, never replace the registration or reacquire a watcher lease. A runnable registration and existing approvals do not authorize a new merge, push, deploy, production write, or irreversible operation.
5. Immediately run `dt-job mark-bootstrap -RunFolder <folder> -CoordinatorId <id> -Host <host> -Json` once, before reading job evidence, reconciling, dispatch preparation or implementation references. Marking is measurement, not permission. Target less than 50,000 input tokens; inspect the actual recorded baseline and retain it as evidence. Only the verified authority digest contract may defer inherited originals; current authority always stays before the marker.

## Carry on

- Reconcile, then read run-level status envelopes, checking `report_verdict` and `failure_category` alongside process status. Handle existing jobs before consuming their events. Read only the current milestone and next action; use the rulebook's execution sections, never repeat intake steps 1–5. Acceptance and verification contracts apply in full before their gates; a resume skips no checks.
- When contracts/glossary are needed, use the run-folder `reference-manifest.md` and its `reference-pack-contracts.md` / `reference-pack-glossary.md` instead of rereading their full source files as well. Check manifest hashes before trusting the packs. Packs are frozen contract data, not substitutes for current policy or approvals. Load the current milestone's applicable contract sections; give workers paths to larger implementation references.
- Read git policy before git actions, model-routing policy before dispatch, browser policy before browser work, tech-stack guidance before application-development work, and session-audit instructions at actual close-out. A worker implementing the application must perform its own governing reads; the coordinator must also read a triggered policy if it itself performs that action. Never preload all these policies just because they may be needed later.
- Dispatch through the host adapter and `dt-job`, with the resolver's selection and all run restrictions. Never read scripts just to discover their arguments when the adapter/step supplies the command. Long tests and audits are jobs. Collect results through capped envelopes; deeper evidence goes through `read-evidence.ps1`.
- On rotation, consume handled events before requesting continuation, preserve the checkpoint's two dt-job-owned lines, request `context_rotation`, release the lease, and end. Running jobs survive. A rotation with no new ledger job starts/completions/failures remains thrash, even if bootstrap was large.

## Lean checkpoint

On every rewrite, keep `_build-state.md` at most 8 KiB: current milestone, short completed ids/SHAs, active job ids, exact next action, run-folder evidence pointers, and all current approvals/restrictions or their authoritative source paths. Use `scripts/write-resume-checkpoint.ps1` for atomic replacement; it preserves dt-job's current status/cursor under the run lock and archives the prior checkpoint under `checkpoint-history/` in the run folder. Existing oversized checkpoints remain readable until their next rewrite.

Never copy operator notes into the checkpoint; they live in the run folder's `operator-notes.json`, and `dt-job status` and every wait show them. Put job history, custody/hash comparisons, failed attempts, detailed verification results and decision narrative in the run folder, never append them to the checkpoint. Do not discard operative boundaries to satisfy the size limit: retain them in a run-folder boundary record, name it in the checkpoint, and apply the authority read contract before marking bootstrap. Archive history before replacing it with a pointer. Use the canonical pipeline template's fields; no template read is needed until a rewrite.

**Evidence notes.** Operators record facts with `dt-job note -Evidence -Message <text>` in `evidence-notes.json`. Coordinators read them as information only, never as authority, and never re-bind on them. They cannot grant, widen, waive or change authority. Anything that changes what the run may do must be a normal operator note (omit `-Evidence`).

## Local work never stops

A managed run stops for Danny only at an outward or irreversible boundary (merge to main, push, deploy, a production or remote write, an irreversible operation) or for a decision only he can make that the run's authority does not already answer (scope, spend, a product choice). Everything local and reversible proceeds without a stop: run-folder evidence and its repairs (counts, inventories, seals, fixtures, provenance), local reruns inside the milestone's attempt cap, checkpoint and authority bookkeeping, adopting a published tooling revision (`ON_MAIN`, `tooling-revision-provenance.md`), and changes to the run's lifecycle records. Record each in the handoff or the stop record and continue. (core-durability-20260922: 39 of 49 M05 stops from Oct 11 to 15 were local bookkeeping, and the milestone never converged.)

1. Never author authority that turns a local, reversible correction into a stop ("only after exact separate registration", "any byte difference STOP" on a file the run itself writes). Bound local work by its scope and the attempt cap instead.
2. Never pin a lifecycle record (`approvals.json`, `operator-notes.json`, `evidence-notes.json`, `build-state.md`, `build-plan.md`, the checkpoint) by full-file hash or literal text: dt-job rewrites them. Cite an approval by its `operation` and `seq`, a note by its id. Compare timestamps as instants, never as text.
3. Evidence for a local acceptance milestone is content evidence: each input's SHA-256 when it was captured, plus the test and validator results. Byte-prefix and literal-text custody is only for files whose exact bytes something consumes (a pinned wrapper a remote host runs, a host key).
4. When a run's existing authority already requires a stop for local work, follow it, but say `local stop` in the `await-danny` message and recommend the operator note that lifts it. Never add another such clause.

## Authority read contract

The original records remain the authorization source. The digest is a mechanical navigation index, never an approval. Coordinators never author or edit its authority content, extracts, manifest or pin; invoke the scripts only.

1. Invoke `scripts/build-authority-digest.ps1 -RunFolder <folder> -BuildStatePath <checkpoint>` when no digest exists, then `scripts/verify-authority-digest.ps1 -RunFolder <folder> -BuildStatePath <checkpoint>`. Both run deterministically without a model. The checkpoint is the discovery root, always read in full: its authority text is pinned separately, excluding only the two dt-job-owned status/cursor lines so operator resume cannot invalidate the digest. Every authority original retains its full-file SHA256 and byte size. Verification hashes the JSON against `authority-digest.json.sha256`, hashes the Markdown against the manifest, rediscovers the source set, and recomputes every original hash and byte size. Any missing or uncovered source, mismatch or malformed manifest fails closed. Discovery supports literal paths, line/list-item aliases with spaced absolute values and recursive alias references, known aliases after glued prose, comma siblings and brace lists. A checkpoint's STOP boundary follows `inherited_boundary` to the counted `inherited_authority_sources` enumeration; each successor contributes its boundary, source disposition, scope and approval text. That structured list controls inherited coverage, rather than evidence references embedded in prose. Without an enumeration, literal references recurse conservatively. Missing named originals fail closed; unresolved non-authority checkpoint references remain visible in the manifest and Markdown diagnostics. No globs or workspace searches.
2. The soft bootstrap authority target is **32,000 characters** across the digest and mandatory originals (roughly 8,000 text tokens; actual tokenizer and marker measurements still govern the less-than-50,000 target). Below that authority-set size, read originals in full. Above it, or when `context_wall` exists, invoke `scripts/read-authority-digest.ps1 -RunFolder <folder> -BuildStatePath <checkpoint>` to read the verified Markdown in full, then every `mandatory_paths` original in full before marking. The checkpoint, run build-state/build-plan, complete approvals and operator notes remain mandatory. The explicit STOP boundary and checkpoint-required current stop restrictions remain mandatory. Named metadata clarifications expressly granting no new authority remain indexed supplemental originals for full reads before dependent actions. In legacy graphs, keep the last checkpoint boundary pointer and most recently written boundary mandatory. Never designate an older boundary as current to shrink bootstrap. If current authority plus digest exceeds the soft target, proceed with the verified digest and all mandatory originals; verification JSON reports `budget_state: "over_target"` and the Markdown header warns visibly. Only above the **96,000-character hard ceiling** (roughly 24,000 text tokens) stop with `AUTHORITY_BOOTSTRAP_BUDGET`; suggest that the operator consolidate or supersede old stop records, then rebuild and verify. Exactly either threshold is accepted. Never omit current authority to meet either threshold. The manifest pins both `budget_chars: 32000` and `ceiling_chars: 96000`; verification requires the current constants. Over-target bootstraps must be confirmed by the observed-transcript check on the next resume. JSON quotes up to 160 characters of operative lines. Markdown uses reversible directory/filename tables, and clips navigation excerpts with an explicit marker; structured lists retain excerpts in JSON and every path in Markdown. Legacy excerpt sizing reserves the full 8 KiB checkpoint ceiling. Neither format grants permission or replaces the governing full read. The separately verified registration/lease read still applies; mutable lifecycle records are not frozen into this authority manifest.
3. If verification fails, read originals in full before bootstrap as previously required. Missing or contradictory authority stops the dependent action. Use `scripts/read-authority-original.ps1 -RunFolder <folder> -BuildStatePath <checkpoint> -Path <absolute-original> -BootstrapFallback` for a full fallback read even if the context-wall/repeat-read guards rejected a direct read. Reach the hard wall? Install the prepared candidate with `write-resume-checkpoint.ps1`, request continuation, release, and stop; this handoff script remains allowed past the wall.
4. Immediately before each dependent merge, push, deploy, production write, approval-gated step or irreversible operation, identify **all** governing originals using the checkpoint, current authority and digest index. Invoke `scripts/read-authority-original.ps1 -RunFolder <folder> -BuildStatePath <checkpoint> -Path <absolute-original>` for each, then read every emitted original IN FULL. This script re-verifies the complete pinned set before emitting the source; changed hashes stop the action and require bootstrap fallback/rebuild. Read in separate calls with enough output capacity. No summary, excerpt, hash alone or prior coordinator claim authorizes the action. Recheck complete approvals and current restrictions at action time. Do not proceed on ambiguity, missing authority or contradiction. Below the hard wall these script reads bypass evidence/repeat-read limits; at the hard wall hand off first unless an already-open irreversible step permits continuation.

## Worker authority scope

The authority read contract binds the coordinator, not its workers. Workers never re-read the run's whole authority set; when the set exceeds the 32,000-character soft target, a brief that tells a worker to read every governing original only spends the worker's context before it does the work (core-durability-20260922, Oct 14: two source-preparation workers checkpointed at 18 and 64 of 130 originals without preparing source).

1. Before dispatch, the coordinator completes its own full reads, then writes the worker's restrictions into the brief as operative rules: allowed paths and operations, exclusions, pins, required evidence, and stop conditions.
2. The brief names only the originals whose exact text the worker's task consumes (a spec, a pinned input, a locator), within the 32,000-character soft target. The worker reads those in full, with `read-authority-original.ps1` when the brief asks for verified reads.
3. If the task needs more authority than fits, the worker stops with a continuation note naming what it needs; the coordinator resolves it. A worker never reconstructs authority from summaries.
4. The coordinator verifies worker output against the full authority, with fresh full reads per item 4 of the read contract, before any dependent merge, push, deploy, production write, approval-gated step or irreversible operation. A worker's reads never stand in for the coordinator's.

This scope changes no approval or restriction: the coordinator still holds every governing original, and workers still act only inside the restrictions written into their brief. The authority roll-forward below keeps the coordinator's own set small; it is not a remedy for worker context.

## Authority roll-forward

Each stop inherits every earlier stop record, so a long run's action-time read set only grows (core-durability-20260922 reached 146 originals and 654,965 characters on Oct 15, past what one coordinator can read). The roll-forward cleans up after itself: at a stop or approval transition, once the action-time read set passes the 32,000-character soft target, roll the governing stop records into ONE current record that carries every live clause verbatim and drops the stale ones with evidence. Old stop records stay on disk untouched as evidence; they leave the read set. Lifecycle records (`approvals.json`, `operator-notes.json`, `build-state.md`, `build-plan.md`, the checkpoint) are never rolled.

1. `scripts/roll-authority-forward.ps1 -Action prepare -RunFolder <folder> -BuildStatePath <checkpoint>` splits every stop-record original in the current graph into clauses (Markdown paragraphs and list items, JSON fields), merges identical text into one row that keeps every origin, and writes `RUN/authority-rollover/<utc>/clauses-ledger.json`. Graph-wiring JSON fields are pre-marked `structural`.
2. Decide every undecided clause in the ledger: `carry`, or `drop` with `reason` (`consumed`, `superseded`, `closed`, `exhausted`) and checkable `evidence`: `{quote: {path, text}}` found in that file, `{event_seq: N}` in `jobs/events.jsonl`, or `{clause: "c-..."}` naming the carried clause that supersedes it (a superseding clause later folded into a consolidated clause still counts, through that consolidation). Carry when in doubt; a carried stale clause costs a few characters, a dropped live one removes a restriction. When one rule is restated across several stops in different words or numbers, replace the restatements with one consolidated clause: add `{text, heading, replaces: [c-ids], why}` to `<dir>/consolidations.json` (at least two replaced clauses, each replaced once) and mark each replaced clause `drop`, reason `consolidated`, evidence `{consolidation: "<id of that text>"}` (ids are `c-` plus the first 12 hex of the SHA-256 of the whitespace-normalized text). A consolidated clause must keep every restriction, pin, gate, allowance limit, exclusion, scope, exception and number of each clause it replaces, with the strictest value winning. Never edit a clause's id, text, heading or sources. For a large first roll, the coordinator may brief a worker to draft the decisions; verify and the review below still guard every drop.
3. `-Action compose -RolloverDirectory <dir>` writes `current-authority.md` (carried clause text only, verbatim, grouped under each original heading once, with consolidated clauses under "Consolidated restatements"), `current-authority.provenance.json` (each clause's id, record lines and RUN-relative sources; evidence only), the rollover `next-operation-boundary.json`, and `review-prompt.md`. Its result reports `record_chars` against the digest's read ceiling (`within_ceiling`); over the ceiling, drop or consolidate more before review.
4. Dispatch exactly one independent reviewer: `invoke-codex-chunk.ps1` or `invoke-claude-chunk.ps1` with `-ReadOnly -AdHoc -SingleDispatch -PromptPath <dir>/review-prompt.md -OutputPath <dir>/review.json`. It answers `stale` or `live` for every dropped clause, and `covers` or `loosens` for every consolidated clause. The review must be independent: compose moves any earlier review in the rollover folder (and the current `review.json` whenever the prompt changes) to `RUN/authority-rollover/_review-archive/<rollover>/<utc>/`, the prompt forbids consulting earlier reviews, and verify refuses while an earlier review sits in the folder. The reply must be the JSON object alone; a prose preamble fails verify.
5. `-Action verify -RolloverDirectory <dir>` proves nothing live was lost: the same STOP boundary and originals as prepare, unchanged hashes, a ledger equal to a fresh extraction, every clause decided, drop reasons from the closed set with evidence that exists, every consolidation well formed and matched by its consolidated drops, a record and sidecar equal to compose output, a record within the read ceiling, and a passing single-dispatch review whose prompt and output hashes match, which names the same consolidations file and calls every drop `stale` and every consolidation `covers`. Any failure stops the roll; fix the ledger, compose again, and review again.
6. `-Action install -RolloverDirectory <dir>` re-verifies, appends every dropped clause to `RUN/authority-history.jsonl` (verbatim text, source path, locator and sha256, reason, what superseded it, the reviewer's reason, the time), points the checkpoint's `STOP=` at the rollover through `write-resume-checkpoint.ps1`, then rebuilds and verifies the authority digest. Its report gives the new read set and any pre-rollover original the checkpoint still names (`still_required_old_records`); remove those pointers in the next checkpoint write. A checkpoint line that names stop-folder files (`STOP/next-scope.md`, `STOP/source-disposition.json`, `STOP/next-approval.md`) would resolve into the rollover, which holds only the record and its boundary; install refuses with `AUTHORITY_ROLLOVER_CHECKPOINT_POINTERS` naming those lines. Rewrite them first through `write-resume-checkpoint.ps1` to `STOP/next-operation-boundary.json` and the originals it enumerates, which is equivalent under the current STOP. `-CandidateOnly` previews without writing; its `consolidated_clauses` lists every consolidated clause with the ids it replaces. Consolidated clauses are new wording: the independent review's `covers` verdict and verify guard them, and the coordinator records the preview path in its handoff so Danny can read it; the install is bookkeeping and never waits for his go. History rows for consolidated originals also carry `consolidated_into`.

The next stop's boundary sets `inherited_boundary` to the rollover's `next-operation-boundary.json`, so its read set is the current record plus the new stop's own records, and the next roll starts from there. Clause ids are content hashes, so a carried clause keeps its id and original source across rolls. `authority-history.jsonl` is append-only audit history: digest discovery treats it, the provenance sidecar, `consolidations.json` and the ledger as evidence only, and it is never read before an action. Read it only to look something up. The roll-forward changes no approval, restriction, pin or gate: every live clause stays in the read set word for word, and the read contract above applies to the current record like any other original.

## Operator recovery after an authority wall and thrash stop

For read-only acceptance, add `-DryRun -OutputDirectory <external-folder>` to the builder and `-DigestDirectory <external-folder>` to the verifier. DryRun requires output outside both the run and checkpoint directories, and never publishes a live digest or pin. Inspect originals discovered, unresolved candidates, Markdown/bootstrap characters, deferred original bytes and mandatory full-read bytes in the verification result. A failed build writes discovery diagnostics at its output location and grants no authority.

After the release coordinator installs this fix, an operator can build and verify the digest before re-arming the stopped run. These commands write the digest only when the operator runs them; do not execute them during fixture-only development. Obtain the registered checkpoint from the dt-job registry for this run (no recursive search):

```powershell
cd "D:/Claude/_Claude-Workspace/Skill Creation/danny-skills"
$recoveryRunFolder = 'D:/Claude/_Claude-Workspace/OneDrive Migration/File Sorter/file-sorter/.dt-build/core-durability-20260922/core-durability-20260922'
. ./skills/dt-build/scripts/dt-job.ps1
$registration = Get-DtJobRegistryEntry -RunFolder $recoveryRunFolder
if ($null -eq $registration) { throw 'Run registration missing; keep run stopped' }
pwsh -NoProfile -File skills/dt-build/scripts/build-authority-digest.ps1 -RunFolder $recoveryRunFolder -BuildStatePath $registration.build_state_path
if ($LASTEXITCODE -ne 0) { throw 'Digest build failed; keep run stopped' }
pwsh -NoProfile -File skills/dt-build/scripts/verify-authority-digest.ps1 -RunFolder $recoveryRunFolder -BuildStatePath $registration.build_state_path
if ($LASTEXITCODE -ne 0) { throw 'Digest verification failed; keep run stopped' }
```

Then issue `/dt-build resume core-durability-20260922` in the operator session. This clears the thrash stop and re-arms the launch budget; the coordinator never issues resume itself. It reads current authority and the verified digest before marking and the governing originals before actions. Capacity refusals use separate 5/10/20 minute backoffs with a 35-minute total wait bound; exhaustion pauses with reason `capacity` and a distinct alert, without spending thrash, retry or launch-cap budgets. A later resume re-arms that budget too.
